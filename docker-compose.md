# Розбір `docker-compose.yaml`

Файл: [`docker-compose.yaml`](docker-compose.yaml). Один сервіс, один контейнер, один том. Нижче кожен блок пояснено окремо, а в кінці — типові правки.

## Чим це відрізняється від офіційного compose-файлу

Офіційний `docker-compose.yaml` з документації Airflow піднімає сім контейнерів: Postgres, Redis, api-server, scheduler, dag-processor, triggerer, Celery-воркер і ще один для ініціалізації. Так виглядає продакшен, але для навчання це зайве: важче стартує, з'їдає 4+ ГБ пам'яті, і при першій помилці незрозуміло, куди дивитися.

Тут усе те саме, але в одному процесі. Про те, які компоненти всередині і що вони роблять, — у [демо 0](dags/demo_00_architecture/README.md).

## Блок за блоком

### `image: apache/airflow:3.3.1`

Офіційний образ, версія зафіксована точно. Не пишіть `latest`: конспекти й параметри в демо звірені саме з 3.3.1, а між мінорними версіями Airflow 3 змінюється помітно.

### `command: standalone`

Замість чотирьох окремих сервісів — одна команда, яка при старті:

1. створює базу метаданих, якщо її ще нема (SQLite у файлі `/opt/airflow/airflow.db`);
2. запускає в одному процесі api-server, scheduler, dag-processor і triggerer;
3. пише в лог рядок `Airflow is ready`, коли все піднялося.

Executor за замовчуванням — `LocalExecutor`: задачі виконуються паралельно в підпроцесах цього ж контейнера.

### `ports: "8080:8080"`

Ліворуч порт на вашому комп'ютері, праворуч — усередині контейнера. Зайнятий 8080 — міняйте ліву частину: `"8081:8080"` і відкривайте http://localhost:8081.

### `environment`

Будь-яке налаштування Airflow можна задати змінною середовища за схемою `AIRFLOW__СЕКЦІЯ__КЛЮЧ`, два підкреслення між частинами. Це те саме, що правити `airflow.cfg`, але файл лишається недоторканим і все видно в одному місці.

| Змінна | Навіщо |
|---|---|
| `AIRFLOW__CORE__LOAD_EXAMPLES: "false"` | Не показувати кілька десятків демонстраційних DAG-ів самого Airflow. У списку тільки ваші |
| `AIRFLOW__CORE__SIMPLE_AUTH_MANAGER_ALL_ADMINS: "true"` | Вхід без логіна і пароля. Тільки для локального навчання: у продакшені так робити не можна |

Значення завжди в лапках: YAML інакше перетворить `false` на булеве значення, а Airflow чекає рядок.

Дві спеціальні родини змінних, які створюють не налаштування, а об'єкти в Airflow:

| Префікс | Що створює | Приклад |
|---|---|---|
| `AIRFLOW_VAR_<ІМ'Я>` | Variable з іменем `ім'я` малими літерами ([демо 13](dags/demo_13_variables/README.md)) | `AIRFLOW_VAR_ROWS_LIMIT: "500"` → `Variable.get("rows_limit")` |
| `AIRFLOW_CONN_<ІМ'Я>` | Connection з `conn_id` `ім'я` ([демо 14](dags/demo_14_postgres/README.md)) | `AIRFLOW_CONN_DEMO_POSTGRES: "postgresql://..."` → `conn_id="demo_postgres"` |

Такі змінні й підключення **не видно** в Admin → Variables і Admin → Connections: вони не в базі, Airflow читає їх з оточення при кожному зверненні. Зате їх видно у файлі, а це зручно для навчання.

### `volumes`

```yaml
- airflow-home:/opt/airflow      # іменований том
- ./dags:/opt/airflow/dags       # папка з комп'ютера
```

Два різні механізми:

- **Іменований том** `airflow-home` живе всередині Docker. Туди Airflow пише базу, логи задач, конфіг. Вам ці файли не потрібні, а от Airflow потрібно, щоб вони пережили перезапуск. Видаляється тільки командою `docker compose down -v`.
- **Bind mount** `./dags` — ваша папка, підключена в контейнер. Файл, збережений в редакторі, одразу видно всередині. Саме тому DAG processor підхоплює зміни без перезапуску.

Порядок важливий: спочатку том на весь `/opt/airflow`, потім папка поверх його підпапки `dags`.

### `healthcheck`

Docker раз на 15 секунд запитує `/api/v2/version`. Поки відповіді нема, контейнер має статус `starting`, після — `healthy`. Перші 90 секунд (`start_period`) невдачі не рахуються: стільки може тривати створення бази при першому запуску. Статус видно в `docker compose ps`.

### `restart: unless-stopped`

Контейнер сам піднімається після перезавантаження комп'ютера або падіння. Не піднімається лише після явного `docker compose stop`.

## Типові правки

**Швидше підхоплювати нові файли.** За замовчуванням папка пересканується раз на 5 хвилин. Для навчання зручніше 30 секунд:

```yaml
environment:
  AIRFLOW__DAG_PROCESSOR__REFRESH_INTERVAL: "30"
```

Зміни в *наявному* файлі й так підхоплюються швидко, це стосується лише появи нових файлів.

**Postgres для демо 14 прямо в compose.** Якщо під рукою нема бази, додайте другий сервіс і підключення до нього:

```yaml
services:
  airflow:
    environment:
      AIRFLOW_CONN_DEMO_POSTGRES: "postgresql://demo:demo@postgres:5432/demo"
    depends_on:
      - postgres

  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: demo
      POSTGRES_PASSWORD: demo
      POSTGRES_DB: demo

volumes:
  airflow-home:
```

Хост у рядку підключення — `postgres`, тобто ім'я сервісу: контейнери в одному compose-файлі бачать один одного за іменами. `localhost` усередині контейнера Airflow — це сам контейнер Airflow, не ваша машина.

**Доставити провайдер, якого нема в образі.** Найпростіше для навчання:

```yaml
environment:
  _PIP_ADDITIONAL_REQUIREMENTS: "apache-airflow-providers-mongo"
```

Пакет ставиться при кожному старті контейнера, тому старт стає повільнішим. Для чогось серйознішого за навчання збирають власний образ.

**Зайти всередину.** Будь-яку команду `airflow` можна виконати в контейнері:

```bash
docker compose exec airflow airflow dags list
docker compose exec airflow bash          # відкрити shell
```

**Почати з чистого аркуша.** `docker compose down -v` видаляє контейнер разом із томом: база, історія запусків, логи і Variables з інтерфейсу зникають. Папка `dags` не чіпається.

## Що з цього не годиться для продакшену

SQLite замість Postgres, `standalone` замість окремих сервісів, вхід без пароля, `LocalExecutor` на одній машині. Усе це нормально для ноутбука і курсу, але для реальної системи беріть офіційний compose або Helm-чарт для Kubernetes.
