# Демо 4. XCom — обмін даними між задачами

Файл: [`dags/demo_04_xcom.py`](../dags/demo_04_xcom.py)

## Ідея

Кожна задача виконується в окремому процесі, часто на іншій машині. Звичайні змінні Python між ними не живуть. XCom (cross-communication) — це таблиця в базі метаданих Airflow, куди задача кладе значення, а інша його забирає.

Ключове обмеження: **XCom — це рядок у базі, а не файл**. Туди кладуть числа, короткі рядки, шляхи, ідентифікатори. Не датафрейми.

## Два способи

### Неявний — через `return`

```python
@task
def count_rows() -> int:
    return 1500          # Airflow сам поклав у XCom під ключем "return_value"

@task
def report(rows: int): ...

report(count_rows())     # і сам забрав
```

Так пишуть у 95% випадків.

### Явний — `xcom_push` / `xcom_pull`

Потрібен, коли з однієї задачі треба віддати **кілька різних** значень:

```python
ti = get_current_context()["ti"]
ti.xcom_push(key="file_path", value="/data/orders.csv")
ti.xcom_push(key="file_size", value=2048)
...
ti.xcom_pull(task_ids="push_many", key="file_path")
```

| Метод | Параметри | Примітка |
|---|---|---|
| `xcom_push` | `key`, `value` | Ключ `return_value` — той, що використовує `return` |
| `xcom_pull` | `task_ids`, `key`, `dag_id`, `include_prior_dates`, `map_indexes` | `task_ids` списком → повернеться список значень |

Альтернатива явному push — `multiple_outputs`:

```python
@task(multiple_outputs=True)
def get_file() -> dict:
    return {"path": "/data/orders.csv", "size": 2048}

info = get_file()
use(info["path"])        # окремий XCom на кожен ключ
```

Якщо анотація типу — `dict`, Airflow вмикає `multiple_outputs` сам.

## Обмеження за розміром

XCom зберігається в колонці бази. Ліміт залежить від бекенда:

| База метаданих | Практичний ліміт |
|---|---|
| SQLite (це середовище) | ~1 ГБ теоретично, але повільно вже на мегабайтах |
| PostgreSQL | 1 ГБ на значення |
| MySQL | 64 КБ (`LONGTEXT` — 4 ГБ, але за замовчуванням менше) |

Незалежно від ліміту: великі значення роздувають базу, гальмують інтерфейс і не чистяться самі. Правильний підхід для великих даних:

```python
@task
def extract() -> str:
    df.to_parquet("/data/staging/orders.parquet")
    return "/data/staging/orders.parquet"     # у XCom іде ШЛЯХ
```

Для постійної роботи з великими об'ємами налаштовують **custom XCom backend** (`AIRFLOW__CORE__XCOM_BACKEND`) — він прозоро кладе значення в S3/GCS, а в базі лишає посилання.

## Що можна класти

Значення має серіалізуватися. Працюють: `int`, `float`, `str`, `bool`, `list`, `dict`, `datetime`, `date`, а також вкладені комбінації. Не працюють: з'єднання з базою, файлові об'єкти, кастомні класи без реєстрації серіалізатора.

## Де подивитися

Інтерфейс: сторінка задачі → вкладка **XCom**. Там видно ключ і значення кожного запису.

## Типові помилки

| Симптом | Причина |
|---|---|
| `xcom_pull` повернув `None` | Не той `task_ids` або `key`; задача-джерело не відпрацювала |
| Значення є, але це рядок замість числа | Забрали зі стрілки `>>`, а не з `return`; або значення від `BashOperator` |
| База розпухла | У XCom кладуть датафрейми. Класти треба шлях |
| Дані з попереднього запуску | `include_prior_dates=True` — вмикайте свідомо |

## Що спробувати

- Відкрити вкладку XCom у задачі `push_many` і побачити обидва ключі.
- Додати `@task(do_xcom_push=False)` і переконатися, що `return` більше нікуди не потрапляє.
