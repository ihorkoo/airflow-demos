# Демо 15. Assets — запуск за готовністю даних

Файл: [`dags/demo_15_assets.py`](../dags/demo_15_assets.py)

## Ідея

Досі DAG запускався або вручну, або за годинником ([демо 12](demo_12_schedule.md)). Asset дає третій варіант: **розклад — це дані, а не час**.

Класична проблема: DAG `load_orders` працює о 02:00, DAG `build_report` — о 03:00. Годину поставили «із запасом». Одного дня завантаження триває півтори години — звіт будується по вчорашніх даних і ніхто цього не помічає. З Asset-ами звіт стартує тоді, коли завантаження реально завершилось: ні раніше, ні на годину пізніше.

## Як це виглядає

```python
orders_raw = Asset(name="orders_raw", uri="file:///opt/airflow/data/orders_raw.csv")

# ПОСТАЧАЛЬНИК: успішне завершення задачі = набір оновився
@task(outlets=[orders_raw])
def load_orders(): ...

# СПОЖИВАЧ: замість розкладу — список наборів
@dag(schedule=[orders_raw, customers_raw])
def consumer(): ...
```

У демо два DAG-и. Запускати треба **лише** `demo_15_assets_producer` — `demo_15_assets_consumer` стартує сам після того, як обидві задачі постачальника відпрацюють.

## Що таке Asset насправді

Asset — це **мітка**, а не самі дані. Airflow не читає ваш файл, не перевіряє його існування й не знає, що всередині. Він лише фіксує: «задача з `outlets=[orders_raw]` завершилася успішно → набір `orders_raw` оновлено» і будить тих, хто на нього підписаний.

Звідси два висновки:
- URI може вказувати на що завгодно — файл, таблицю, S3, зовнішній API. Це ідентифікатор, а не шлях, яким Airflow ходить.
- Якщо задача завершилась успішно, але файл не записала, подія все одно згенерується. Відповідальність за чесність — на вас.

## Довідка: параметри `Asset`

| Параметр | Значення за замовч. | Що робить |
|---|---|---|
| `name` | з `uri` | Ім'я набору. Показується в інтерфейсі |
| `uri` | з `name` | Ідентифікатор. Має бути валідним URI без пробілів |
| `group` | `""` | Група для впорядкування на сторінці Assets |
| `extra` | `{}` | Статичні метадані набору |
| `watchers` | `[]` | Тригери, що оновлюють набір від зовнішніх подій (черга, черга повідомлень) |

Задається принаймні одне з `name` / `uri`. Найзрозуміліше — обидва.

## Довідка: логіка розкладу

| Запис | Коли спрацює |
|---|---|
| `schedule=[a]` | Оновився `a` |
| **`schedule=[a, b]`** | Оновились **обидва** — це І |
| `schedule=AssetAny(a, b)` | Оновився хоч один — це АБО |
| `schedule=AssetAll(a, b)` | Те саме, що список: обидва |
| `AssetAny(a, AssetAll(b, c))` | Комбінації вкладаються |
| `AssetOrTimeSchedule(timetable=CronTriggerTimetable("0 6 * * *", timezone="UTC"), assets=[a])` | За розкладом **або** коли оновились дані |

`AssetAll` чекає оновлення кожного набору **хоча б раз** із моменту попереднього запуску. Якщо `a` оновився тричі, а `b` жодного — запуску не буде.

## Передавання даних разом із подією

Подію можна супроводити метаданими, і споживач їх прочитає:

```python
@task(outlets=[customers_raw])
def load_customers():
    ...
    yield Metadata(customers_raw, {"row_count": 3, "file": str(path)})
```

Другий спосіб — через контекст:

```python
context["outlet_events"][customers_raw].extra = {"row_count": 3}
```

На боці споживача:

```python
events = get_current_context()["triggering_asset_events"]
for asset_uri, event_list in events.items():
    for event in event_list:
        print(event.extra)
```

Це **не заміна XCom**: XCom працює між задачами одного запуску, `extra` — між різними DAG-ами. Обмеження ті самі: короткі значення, не датафрейми.

## `@asset` — скорочений запис

Коли DAG існує заради одного набору даних, є компактніша форма:

```python
from airflow.sdk import asset

@asset(schedule=None, uri="file:///opt/airflow/data/orders_raw.csv")
def orders_raw():
    ...                # тіло функції = задача, що оновлює цей набір
```

Один декоратор створює і DAG, і задачу, і сам Asset. Зручно для шару «одна таблиця — один пайплайн», але менш наочно для навчання, тому в демо використано явний варіант.

## Asset vs сенсор vs розклад

| Підхід | Коли брати | Ціна |
|---|---|---|
| **Asset** | Обидва DAG-и ваші | Безкоштовно — жодного слота не займає |
| **`ExternalTaskSensor`** | Другий DAG ваш, але потрібен зв'язок із конкретним запуском | Займає слот або переплановується |
| **Сенсор на файл** ([демо 11](demo_11_sensor.md)) | Джерело зовнішнє і про Airflow не знає | Займає ресурси на очікування |
| **Розклад із запасом** | Крайній випадок | Крихкий: ламається при кожній затримці |

Правило: якщо обидва боки у вашому Airflow — беріть Asset.

## Де подивитися в інтерфейсі

Пункт меню **Assets**: список наборів, граф залежностей «хто виробляє → хто споживає», історія подій із `extra`. Це найкорисніша сторінка, коли пайплайнів стає багато — вона показує потік даних, а не окремі DAG-и.

## Типові помилки

| Симптом | Причина |
|---|---|
| Споживач не стартує | Оновився не кожен набір зі списку — `[a, b]` означає І |
| Споживач не стартує, хоч усе оновилось | DAG-споживач стоїть на паузі |
| Подія не згенерувалась | Задача-постачальник впала. Подія — лише при статусі `success` |
| Спрацювало одразу, хоч оновився один набір | Написали `AssetAny` замість списку |
| Два DAG-и не бачать один одного | `name`/`uri` мають збігатися **посимвольно** |
| `Invalid URI` | Пробіли або кирилиця в `uri` |
| Споживач запустився двічі | Постачальник оновив набір двічі — це нормальна поведінка |

## Що спробувати

- Запустити `demo_15_assets_producer` і подивитися, як за хвилину сам стартує споживач.
- Відкрити в споживача лог задачі `show_trigger_reason` — там видно `extra` з кількістю рядків.
- Поставити споживачу `schedule=AssetAny(orders_raw, customers_raw)` і побачити, що тепер він стартує двічі — після кожної задачі постачальника.
- Зайти в меню **Assets** і подивитися граф залежностей.
