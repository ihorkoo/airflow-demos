# Демо 11. Сенсори

Файл: [`demo_11_sensor.py`](demo_11_sensor.py)

## Ідея

Сенсор — це задача, яка чекає на подію: поява файлу, готовність таблиці, відповідь від зовнішньої системи. Вона періодично перевіряє умову («poke») і завершується успіхом, щойно умова виконалась.

Сенсор потрібен там, де ваш пайплайн залежить від чужого розкладу, який ви не контролюєте.

## Як це виглядає

```python
@task.sensor(poke_interval=5, timeout=60, mode="reschedule")
def wait_for_file() -> bool:
    return FLAG_FILE.exists()      # True — готово, False — чекаємо далі
```

Функція повертає `True` або `False`. Можна повернути `PokeReturnValue(is_done=True, xcom_value=...)`, щоб віддати наступній задачі ще й дані.

## Довідка: параметри сенсора

| Параметр | Значення за замовч. | Що робить |
|---|---|---|
| **`poke_interval`** | 60 с | Як часто перевіряти |
| **`timeout`** | `None` | Скільки секунд чекати, перш ніж здатися |
| **`mode`** | `"poke"` | `poke` — тримати слот увесь час; `reschedule` — звільняти між перевірками |
| `soft_fail` | `False` | При таймауті ставити `skipped`, а не `failed` |
| `exponential_backoff` | `False` | Збільшувати інтервал перевірок із часом |
| `max_wait` | `None` | Стеля інтервалу при backoff |
| `silent_fail` | `False` | Не валити задачу при помилці всередині перевірки |
| `never_fail` | `False` | Завжди `skipped` замість `failed` |

## `poke` чи `reschedule` — головне рішення

| | `poke` | `reschedule` |
|---|---|---|
| Слот воркера | зайнятий увесь час очікування | звільняється між перевірками |
| Накладні витрати | мінімальні | старт задачі на кожну перевірку |
| Коли брати | чекати менше ~5 хвилин | чекати довго: години, до кінця дня |

Це найважливіший параметр сенсора. Десять сенсорів у режимі `poke`, що чекають по годині, займуть десять слотів і **заблокують увесь Airflow** — класичний спосіб покласти собі середовище. У режимі `reschedule` слот на час паузи вільний.

Кількість переплануваннь видно в контексті як `task_reschedule_count`.

## Готові сенсори

| Сенсор | Чекає на |
|---|---|
| `FileSensor` | Файл або маску шляху |
| `PythonSensor` | `True` від вашої функції (те саме, що `@task.sensor`) |
| `TimeDeltaSensor` / `DateTimeSensor` | Настання моменту часу |
| `ExternalTaskSensor` | Задачу або DAG в іншому DAG-у |
| `SqlSensor` | Непорожній результат SQL-запиту |
| `HttpSensor` | Відповідь HTTP-ендпойнта |
| `S3KeySensor` | Об'єкт у S3 |

## `timeout` обов'язковий

Без `timeout` сенсор чекатиме вічно. Файл, який не з'явиться ніколи, перетвориться на задачу, що висить тижнями. Ставте `timeout` завжди і робіть його меншим за період розкладу — інакше вчорашній сенсор дочекається сьогоднішнього запуску.

Комбінація `soft_fail=True` + `timeout` дає м'яку поведінку: не дочекались — пропускаємо решту пайплайна, але не будимо чергового.

## Альтернативи сенсору

| Підхід | Коли краще |
|---|---|
| **Asset (data-aware scheduling)** | Обидва DAG-и ваші. DAG-споживач стартує сам, коли DAG-виробник оновив дані. Не витрачає слотів узагалі |
| **Deferrable-оператори** | Чекання віддається окремому процесу `triggerer`, слот не займається. Сучасна заміна довгих сенсорів |
| **Сенсор** | Джерело зовнішнє й нічого про Airflow не знає |

## Типові помилки

| Симптом | Причина |
|---|---|
| Сенсор висить нескінченно | Не заданий `timeout` |
| Усі слоти зайняті, нічого не виконується | Кілька сенсорів у режимі `poke` |
| `reschedule` не працює | Цей режим не підтримують deferrable-оператори |
| Сенсор не бачить файл | Шлях усередині контейнера, а не на хості |
| Сенсор спрацював, а даних немає | Файл існує, але ще дописується. Перевіряйте й розмір |

## Що спробувати

- Прибрати задачу `create_file` і подивитися, як сенсор дійде до таймауту.
- Поставити `mode="poke"` і порівняти поведінку в інтерфейсі.
- Додати `soft_fail=True` і побачити `skipped` замість `failed`.
