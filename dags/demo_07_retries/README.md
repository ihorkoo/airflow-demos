# Демо 7. Повтори при помилці

Файл: [`demo_07_retries.py`](demo_07_retries.py)

## Ідея

Мережа рветься, бази йдуть на обслуговування, API повертає 503. Більшість таких збоїв минають самі за кілька хвилин. Тому задача не має здаватися з першої спроби — вона повторюється.

У демо задача навмисно падає на першій і другій спробі й спрацьовує на третій. Підсумковий статус — `success`, а в логах видно всі три спроби.

## Довідка: параметри повторів

| Параметр | Значення за замовч. | Що робить |
|---|---|---|
| **`retries`** | 0 | Скільки **додаткових** спроб. `retries=3` — максимум 4 запуски |
| **`retry_delay`** | 5 хв | Пауза перед наступною спробою (`timedelta`) |
| `retry_exponential_backoff` | `False` | Подвоювати паузу з кожною спробою: 10с, 20с, 40с, 80с |
| `max_retry_delay` | `None` | Стеля для backoff, щоб пауза не виросла до годин |
| `retry_policy` | `None` | Власна логіка: повторювати лише певні винятки |
| `execution_timeout` | `None` | Убити спробу, якщо триває довше. Без нього зависла задача висітиме вічно |
| `on_retry_callback` | `None` | Функція, що викликається перед кожним повтором |
| `on_failure_callback` | `None` | Викликається після того, як **скінчилися** всі спроби |
| `email_on_retry` / `email_on_failure` | `True` | Лист (потрібен налаштований SMTP) |

## `default_args` — налаштування на весь DAG

```python
@dag(
    default_args={
        "retries": 3,
        "retry_delay": timedelta(seconds=10),
        "owner": "data-team",
    },
)
```

`default_args` застосовується до **всіх** задач DAG-а. Параметр, заданий у самій задачі, перекриває значення зі словника:

```python
@task(retries=0)          # ця задача не повторюється, попри default_args
def save(data: str): ...
```

Порядок пріоритету: параметр задачі → `default_args` DAG-а → конфіг Airflow (`AIRFLOW__CORE__DEFAULT_TASK_RETRIES`).

## `try_number`

Номер поточної спроби, починається з 1. Доступний як `context["ti"].try_number`. У демо саме за ним задача вирішує, падати їй чи ні.

Не плутайте: `max_tries` — це `retries`, а загальна кількість запусків = `retries + 1`.

## Скільки ставити

| Тип задачі | Рекомендація |
|---|---|
| Запит до зовнішнього API | `retries=3..5`, `retry_exponential_backoff=True` |
| Читання з бази | `retries=2..3`, пауза 1–5 хв |
| Важкий перерахунок на годину | `retries=1`, і обов'язково `execution_timeout` |
| Операція, що не є ідемпотентною | `retries=0` — повтор зробить подвійну вставку |

**Ідемпотентність** — головна умова повторів. Задача має давати той самий результат, скільки б разів її не запустили. Практично: не `INSERT`, а `DELETE + INSERT` за період або `INSERT ... ON CONFLICT`. Інакше три спроби дадуть потрійні дані.

## Типові помилки

| Симптом | Причина |
|---|---|
| Повтори не відбуваються | `retries` не задано; за замовчуванням 0 |
| Після повторів дані задублювались | Задача не ідемпотентна |
| Задача висить годинами | Немає `execution_timeout` |
| Повтори «з'їли» все вікно розкладу | Довгий `retry_delay` × багато спроб |
| Повторюється помилка в коді | Повтори лікують збої середовища, а не баги. `TypeError` повторювати марно |

## Що спробувати

- Поставити `retries=1` і побачити, як задача впаде остаточно.
- Додати `retry_exponential_backoff=True` і подивитися в логах, як ростуть паузи.
- Прибрати `retries=0` у `save` — вона успадкує 3 спроби з `default_args`.
