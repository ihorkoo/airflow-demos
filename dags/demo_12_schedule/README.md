# Демо 12. Розклад і catchup

Файл: [`demo_12_schedule.py`](demo_12_schedule.py)

## Ідея

Єдиний DAG у наборі, який працює сам. Решта мають `schedule=None` і чекають натискання кнопки.

Розклад задається параметром `schedule`. У Airflow 2 він звався `schedule_interval` — саме тому код із більшості туторіалів тут не запускається.

## Довідка: формати розкладу

| Значення | Що означає |
|---|---|
| `None` | Тільки вручну або за Asset-ом |
| `"@once"` | Один раз після `start_date` |
| `"@hourly"` | `0 * * * *` |
| `"@daily"` | `0 0 * * *` |
| `"@weekly"` | `0 0 * * 0` — щонеділі опівночі |
| `"@monthly"` | `0 0 1 * *` |
| `"@quarterly"` | `0 0 1 */3 *` |
| `"@yearly"` | `0 0 1 1 *` |
| `"@continuous"` | Наступний запуск одразу після попереднього |
| `"0 6 * * *"` | Cron: щодня о 06:00 |
| `"0 9 * * 1-5"` | Cron: о 09:00 з понеділка по п'ятницю |
| `"*/15 * * * *"` | Cron: кожні 15 хвилин |
| `timedelta(hours=6)` | Кожні 6 годин **від попереднього запуску** |
| `Asset("s3://bucket/orders")` | Коли інший DAG оновив ці дані |
| `CronTriggerTimetable(...)` | Cron без прив'язки до інтервалу даних |
| `AssetOrTimeSchedule(...)` | За розкладом **або** коли оновились дані |

## Cron у двох словах

```
┌── хвилина (0-59)
│ ┌── година (0-23)
│ │ ┌── день місяця (1-31)
│ │ │ ┌── місяць (1-12)
│ │ │ │ ┌── день тижня (0-6, 0 = неділя)
│ │ │ │ │
0 6 * * *
```

`*/15` — кожні 15, `1-5` — діапазон, `1,15` — перелік. Перевіряти вирази зручно на crontab.guru.

## `timedelta` vs cron

Різниця тонка, але важлива. `timedelta(hours=6)` відлічує шість годин **від попереднього запуску**: якщо запуск затримався, весь розклад зсувається. Cron `0 */6 * * *` прив'язаний до годинника: 00:00, 06:00, 12:00, 18:00 — незалежно від затримок.

Для звітів, які мають виходити «о шостій ранку», беріть cron.

## `catchup` — головна небезпека

```python
start_date=datetime(2024, 1, 1)
schedule="@daily"
catchup=True        # Airflow створить ~600 запусків одразу
```

`catchup=True` означає «догнати всі пропущені інтервали від `start_date` до зараз». З датою початку рік тому це сотні одночасних запусків, які кладуть середовище. Саме так найчастіше й ламають собі Airflow.

Захист:

| Інструмент | Дія |
|---|---|
| **`catchup=False`** | Не доганяти. Значення за замовчуванням у всіх демо |
| **`max_active_runs=1`** | Навіть при `catchup=True` запуски йдуть по одному |
| `start_date` недавно | Менше інтервалів для наздоганяння |

`catchup=True` має сенс лише тоді, коли задачі ідемпотентні й ви справді хочете перерахувати історію. Для разового перерахунку краще запустити backfill вручну — в інтерфейсі або командою `airflow backfill create`.

## Логічна дата і зсув

DAG із `@daily` і датою 15 березня стартує **на початку 16 березня**, бо доба 15-го має спочатку закінчитися. Це не затримка, а логіка: обробляється завершений період. Подробиці — [демо 5](../demo_05_context/README.md).

## Пов'язані параметри

| Параметр | Що робить |
|---|---|
| `start_date` | З якої дати рахуються інтервали |
| `end_date` | Після цієї дати запуски не створюються |
| `max_active_runs` | Скільки запусків одночасно |
| `dagrun_timeout` | Убити запуск, що триває занадто довго |
| `is_paused_upon_creation` | Створити DAG уже активним |
| `max_consecutive_failed_dag_runs` | Автопауза після N провалів поспіль |
| `allowed_run_types` | Обмежити типи запусків |

## Типові помилки

| Симптом | Причина |
|---|---|
| `schedule_interval` не розпізнається | Airflow 2. У третій версії — `schedule` |
| Сотні запусків після ввімкнення | `catchup=True` зі старим `start_date` |
| DAG не запускається за розкладом | Стоїть на паузі — перемикач ліворуч у списку |
| Перший запуск не тоді, коли чекали | Запуск відбувається **після** завершення інтервалу |
| Запуски накладаються | Потрібен `max_active_runs=1` |
| `start_date` у майбутньому | Запусків не буде взагалі |

## Що спробувати

- Поставити `schedule="*/5 * * * *"`, зняти з паузи й подивитися автоматичні запуски.
- Поставити `catchup=True` разом із `max_active_runs=1` і побачити, як запуски йдуть по черзі, а не лавиною.
