# Демо 3. Форма графа

Файл: [`demo_03_dependencies.py`](demo_03_dependencies.py)

## Ідея

З тих самих задач можна зібрати різні графи, і саме форма графа визначає, скільки пайплайн працюватиме. Послідовність із трьох завантажень по 2 хвилини — 6 хвилин. Ті самі три паралельно — 2 хвилини.

Дивитися цей DAG треба у вкладці **Graph**.

## Два способи задати залежність

**Через дані** — задача приймає результат іншої:

```python
summarize(orders, customers, products)   # чекає всіх трьох
```

**Через стрілку** — коли дані не передаються, але порядок важливий:

```python
begin >> [orders, customers, products]   # усі три чекають на begin
```

Обидва способи можна змішувати в одному DAG-і. Стрілка потрібна, наприклад, коли перша задача створює таблицю, а друга в неї пише: даних між ними немає, залежність є.

## Базові форми

| Форма | Запис | Коли |
|---|---|---|
| Ланцюжок | `a >> b >> c` | Кроки ETL один за одним |
| Віяло (fan-out) | `a >> [b, c, d]` | Паралельне завантаження джерел |
| Збірка (fan-in) | `[b, c, d] >> e` | Звіт з кількох джерел |
| Ромб | `a >> [b, c] >> d` | Найпоширеніша форма пайплайна |

## Що насправді обмежує паралелізм

Написати `>>` — мало. Задачі підуть одночасно лише якщо це дозволяють налаштування:

| Обмеження | Де задається | За замовчуванням |
|---|---|---|
| Тип виконавця | `AIRFLOW__CORE__EXECUTOR` | `LocalExecutor` — паралелить |
| Задач у межах DAG-а | `max_active_tasks` у `@dag` | 16 |
| Запусків DAG-а одночасно | `max_active_runs` у `@dag` | 16 |
| Задач на всю інсталяцію | `parallelism` у конфігу | 32 |
| Пул | `pool` у задачі | `default_pool`, 128 слотів |

Якщо задачі вперто йдуть по черзі — шукайте причину в цій таблиці, а не в коді DAG-а.

## Хелпери для складних графів

```python
from airflow.sdk import chain, cross_downstream

chain(a, b, c, d)                    # a >> b >> c >> d
chain(a, [b, c], [d, e], f)          # попарно: b>>d, c>>e
cross_downstream([a, b], [c, d])     # кожна з першої групи → кожна з другої
```

`chain` із вкладеними списками з'єднує їх **попарно**, а не «всі з усіма» — це найчастіше непорозуміння з цією функцією.

## Типові помилки

| Симптом | Причина |
|---|---|
| Задача виконується двічі під іменами `x` і `x__1` | Функцію-задачу викликали двічі. Кожен виклик створює **нову** задачу |
| `Cycle detected` | Стрілки замкнулися в кільце |
| Задачі не паралеляться | Див. таблицю обмежень вище |
| `[a, b] >> [c, d]` не працює | Потрібен `cross_downstream` |

## Примітка до коду

У файлі є рядок, що повторює залежності й вдруге викликає `summarize(...)`:

```python
summarize(orders, customers, products)
begin >> [orders, customers, products] >> summarize(orders, customers, products)
```

Другий виклик створює **окрему задачу** `summarize__1` — у графі буде дві однакові вершини. Це наочна ілюстрація правила «виклик = нова задача»: щоб лишилась одна, результат першого виклику треба зберегти у змінну й використовувати її.

## Що спробувати

- Прибрати `begin >> [...]` і подивитися, як три завантаження стануть початковими задачами графа.
- Поставити `max_active_tasks=1` і побачити, що паралелізм зник, хоча граф не змінився.
