# Демо 8. Trigger rules

Файл: [`demo_08_trigger_rules.py`](demo_08_trigger_rules.py)

## Ідея

Стрілка `a >> b` задає *порядок*, але не *умову*. Умову задає trigger rule: за замовчуванням `all_success` — «запускайся, тільки якщо всі попередні успішні». Якщо хоч одна впала, наступні не запускаються взагалі й отримують статус `upstream_failed`.

Для більшості задач це правильно. Але прибирання тимчасових таблиць має виконатися завжди, а сповіщення про збій — навпаки, тільки при збої. Для цього правило змінюють.

## Довідка: усі правила Airflow 3.3.1

| Правило | Запускається, коли |
|---|---|
| **`all_success`** (за замовч.) | Усі попередні успішні |
| **`all_done`** | Усі попередні завершилися — байдуже, як. Для прибирання |
| **`one_failed`** | Хоча б одна впала. Не чекає решти. Для сповіщень |
| **`none_failed_min_one_success`** | Жодна не впала і хоча б одна успішна. Для збірки після розгалуження |
| `all_failed` | Усі попередні впали |
| `one_success` | Хоча б одна успішна, решти не чекає |
| `one_done` | Хоча б одна завершилась успіхом або провалом |
| `none_failed` | Жодна не впала (успішні й пропущені годяться) |
| `none_skipped` | Жодну не пропущено |
| `all_skipped` | Усі попередні пропущено |
| `always` | Завжди, незалежно ні від чого |
| `all_done_min_one_success` | Усі завершилися і хоча б одна успішна |
| `all_done_setup_success` | Усі завершилися і setup-задачі відпрацювали успішно |

Константи замість рядків — `from airflow.sdk import TriggerRule`, далі `TriggerRule.ALL_DONE`.

## Три робочі патерни

**Прибирання, що виконується завжди:**
```python
@task(trigger_rule="all_done")
def cleanup(): ...
```

**Сповіщення про збій:**
```python
@task(trigger_rule="one_failed")
def send_alert(): ...
```

**Збірка після розгалуження:**
```python
@task(trigger_rule="none_failed_min_one_success")
def finish(): ...
```

## Чому DAG зелений, коли задача червона

У цьому демо `load_data` падає навмисно, але весь запуск має статус `success`. Airflow дивиться на **листові** задачі графа — ті, після яких нічого немає. Тут це `cleanup` і `send_alert`, і обидві відпрацювали успішно.

Практичний висновок: зелений DAG не гарантує, що всередині все пройшло гладко. Якщо треба, щоб провал у середині валив весь запуск:

- `fail_fast=True` у `@dag` — перша ж помилка зупиняє запуск;
- або задача-вартовий у кінці, що перевіряє стани й падає сама;
- або `on_failure_callback` на рівні DAG-а.

## Setup і teardown

Окремий механізм для «підготувати ресурс — прибрати ресурс»:

```python
create_cluster = make_cluster().as_setup()
delete_cluster = drop_cluster().as_teardown(setups=create_cluster)
```

Teardown виконується навіть при провалі, **не впливає** на підсумковий статус DAG-а, і при повторному запуску setup запускається разом із тим, що від нього залежить. Для тимчасових кластерів і з'єднань це чистіше за `all_done`.

## Типові помилки

| Симптом | Причина |
|---|---|
| Задача після розгалуження не стартує | Треба `none_failed_min_one_success` |
| Прибирання не виконалось після збою | Треба `all_done` |
| Сповіщення прийшло при успішному запуску | Переплутали `one_failed` з `one_done` |
| `all_done` спрацював, але DAG зелений | Див. розділ про листові задачі |
| `upstream_failed` замість `failed` | Задача не запускалась — впала попередня |

## Що спробувати

- Прибрати `trigger_rule` у `cleanup` і побачити статус `upstream_failed`.
- Додати `fail_fast=True` у `@dag` і порівняти підсумковий статус запуску.
