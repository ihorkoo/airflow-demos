# Демо 16. Моделювання DWH

Файл: [`demo_16_dwh_modeling.py`](demo_16_dwh_modeling.py)

## Ідея

Попередні демо показували по одному механізму Airflow. Це — невеликий, але справжній пайплайн: із двох CSV будуємо зоряну схему для готельних бронювань, перевіряємо її і рахуємо аналітику.

Логіка та сама, що в ноутбуці «Моделювання даних у DWH на pandas». Різниця в тому, що ноутбук виконують зверху вниз руками, а тут кожна таблиця — окрема задача. Airflow сам знає порядок, запускає незалежні таблиці паралельно і перезапускає лише те, що впало.

## Що на вході і на виході

| Файл | Що це |
|---|---|
| `data/bookings.csv` | джерело: одне бронювання в рядку, 405 рядків із дублікатами |
| `data/guests.csv` | джерело: довідник гостей у двох зрізах — 2025-01-01 і 2026-01-01 |
| `staging/bookings.csv`, `staging/guests.csv` | почищені дані, проміжний шар |
| `dim_date.csv` | календар, усі дні поспіль, ключ `YYYYMMDD` |
| `dim_hotel.csv` | готелі |
| `dim_guest.csv` | гості з історією змін (SCD Type 2) |
| `fact_bookings.csv` | один рядок = одне бронювання |
| `fact_monthly.csv` | один рядок = готель × місяць |

Джерела лежать поруч із DAG-ом, результат пишеться в `/opt/airflow/data/dwh/` всередині контейнера.

## Граф

```
staging                dimensions              facts
┌────────────────┐    ┌───────────┐
│ clean_bookings │─┬─▶│ dim_date  │
│                │ ├─▶│ dim_hotel │─┬──▶ fact_bookings ─┐
└────────────────┘ │  └───────────┘ │                   ├─▶ validate ─▶ report
┌────────────────┐ │  ┌───────────┐ ├──▶ fact_monthly ──┘
│ clean_guests   │─┼─▶│ dim_guest │─┘
└────────────────┘ │  └───────────┘
                   └──────────────────▶ (факти теж читають бронювання)
```

Три виміри будуються паралельно, дві таблиці фактів — теж. Факти чекають на виміри, бо беруть із них ключі.

## Як таблиці йдуть між задачами

Через XCom таблиці не передаються: він для маленьких значень ([демо 4](../demo_04_xcom/README.md)). Тому кожна задача пише файл і повертає **шлях до нього**:

```python
@task
def build_dim_hotel(bookings_path: str) -> str:
    bookings = read_table(bookings_path)
    ...
    return save_table(dim_hotel, DWH_DIR / "dim_hotel.csv")   # повертає рядок зі шляхом
```

У вкладці **XCom** будь-якої задачі видно саме рядок на кшталт `/opt/airflow/data/dwh/dim_hotel.csv`.

Це працює, бо всі задачі виконуються в одному контейнері й бачать той самий диск. Якби задачі йшли на різних машинах (Celery, Kubernetes), файли довелося б класти в спільне сховище — S3, базу даних.

## Звідки Airflow знає порядок

Стрілок між задачами майже немає. Залежності виводяться з того, чий результат яка задача отримує:

```python
dim_hotel = build_dim_hotel(bookings)                               # після clean_bookings
fact_bookings = build_fact_bookings(bookings, dim_guest, dim_hotel) # після двох вимірів
```

Єдина стрілка — `validate >> report`. Звіт не бере даних у перевірки, але рахувати його по зламаній моделі немає сенсу.

## Перевірка, яка вміє падати

У ноутбуці перевірка друкує `True` або `False`, і читати це має людина. У пайплайні людини немає, тому `validate` кидає помилку, якщо хоч одна перевірка не пройшла:

```python
failed = [name for name, passed in checks.items() if not passed]
if failed:
    raise ValueError(f"модель не пройшла перевірку: {failed}")
```

Задача стає червоною, `report` не запускається (стан `upstream_failed`).

| Перевірка | Що ловить |
|---|---|
| жодне бронювання не загубилося | рядки зникли під час пошуку версії гостя |
| один рядок на бронювання | розмноження рядків після `merge` |
| один рядок на готель×місяць | дублікати в періодичному зрізі |
| усі ключі є у вимірах | факти посилаються на неіснуючий рядок виміру |
| виторг збігся | метрики спотворилися дорогою |

## Службові колонки

Кожен вимір отримує дві колонки: `dw_load_ts` — коли стартував запуск, `dw_loaded_by` — його `run_id`. У ноутбуці там були час і користувач комп'ютера, у Airflow природний відповідник — сам запуск: за `run_id` видно, який запуск записав рядок, і можна знайти його логи.

## Ідемпотентність

Кожна задача перезаписує свій файл повністю. Скільки разів не запускай DAG — результат однаковий, дублікатів не з'являється. Докладніше про це — у [демо 7](../demo_07_retries/README.md).

## Підводний камінь CSV

CSV не зберігає типи, тому на стиках задач їх треба відновлювати:

| Проблема | Що робимо |
|---|---|
| дати читаються як рядки | `parse_dates=[...]` у `read_table` |
| `"N/A"` і порожній рядок pandas читає як `NaN` | `keep_default_na=False` |

Без другого пункту код рядка Unknown `N/A` став би `NaN`. У справжніх проєктах для цього беруть Parquet: він зберігає типи.

## Типові помилки

| Симптом | Причина |
|---|---|
| `ModuleNotFoundError: pandas` під час розбору DAG-а | `import pandas` стоїть на початку файлу, а не всередині задачі |
| `FileNotFoundError` у задачі фактів | задачу запустили окремо, до вимірів: файлів ще немає |
| У фактах більше рядків, ніж бронювань | після `merge` не відфільтрували версії гостя за датою |
| `validate` червона з «виторг збігся» | бронювання загубилися: дата поза періодами дії версій гостя |
| Задачі не бачать файли одна одної | задачі йдуть на різних машинах, потрібне спільне сховище |

## Що спробувати

- Запустити DAG і відкрити логи `dimensions.build_dim_guest` — там рядок `20 гостей → 26 версій`.
- Подивитися вкладку **XCom** будь-якої задачі: там шлях, а не таблиця.
- Зіпсувати перевірку (наприклад, прибрати `drop_duplicates` у `clean_bookings`) і подивитися, як `validate` зупинить пайплайн.
- Очистити (Clear) лише `facts.build_fact_monthly` — перезапустяться вона, `validate` і `report`, а виміри ні.
- Переглянути результат: `docker exec airflow ls /opt/airflow/data/dwh`.
- Додати задачу з ноутбука, якої тут немає: SCD Type 1, junk-вимір або сніжинку.
